# BEA-1580 — every failure a customer sees ends in one of his six moves

Linear: <https://linear.app/beakn/issue/BEA-1580>

## Why

The owner, on shipping: *"he tried creating an agent, and it failed. How can he fix it?"* A customer
who cannot code has exactly six moves: **read a reason · Run again / Rebuild · say it differently in
chat · "run it the old way" · connect a tool in /tools · wait**. Any failure message that does not
end in one of those is a bug in the message. And plumbing-class failures — OUR infrastructure, not
his ask — must never be presented as his problem at all: *"the worker runner could not be reached"*,
*"kit version is unknown"*, *"no readable meta.json"*, *"NOT_REPEATABLE"* mean nothing to him.

## Where

- NEW shared module, e.g. `api/src/agent/failure-words.ts` — ONE classifier (the BEA-1544 pattern):
  given a failure string/class, answers (a) is it plumbing-class or customer-actionable, and (b) for
  customer-actionable, which of the six moves its message should end in. Export the plumbing classes
  as data — BEA-1581 alerts on exactly these; build the seam now (a `plumbingClassOf(error)` that
  1581 can import), do not build the alerting itself.
- The strings live where failures are born: `worker.controller.ts` (finish/fail), 
  `worker-build.service.ts` (build/check errors), `worker-dispatch.service.ts` (road fallbacks — 
  mostly already info-steps, verify), `worker-sweeper.service.ts` (watchdog/deadline), 
  `worker-repair.service.ts` (pause message), `hermes-bridge.service.ts` (chatEdit — already done in
  BEA-1575, fold its three reasons into the classifier rather than re-wording), 
  `social-agent-run.service.ts`, `flows-runner.service.ts`, and the run screen's failed box
  (`AgentRunView.tsx` already turns "/tools" mentions into a button — keep that pattern).
- Plumbing failures that already fall back to the old road stay exactly as they are — the classifier
  just names them; where one still surfaces raw to the customer, it becomes: "Something on our side
  hiccupped — your agent ran the old way / nothing was lost. It has been noted." with the honest
  internal message kept in the run's error field for us, never invented away.

## Acceptance (WHEN / MUST)

- WHEN a failure is customer-actionable, its user-facing message MUST end in one of the six moves,
  named plainly.
- WHEN a failure is plumbing-class, the customer-facing text MUST NOT ask him to fix our internals;
  the honest internal sentence stays stored on the run/build row (we still need it), and the
  fallback behaviour (retry / old road) is unchanged.
- ONE classifier, exported, with the plumbing classes as data for BEA-1581.
- A locking test walks the real failure strings from the 2026-08-29 audit (they are in the issue and
  in `AgentRun`/`WorkerBuild` history) and asserts each classifies the intended way.
- MUST NOT soften honesty: a real failure still says what happened; the rule adds the NEXT STEP.
- MUST NOT change: BEA-1359 honest empties; BEA-1403's loud doubt (that is a WARNING with a next
  step, classify it customer-actionable); BEA-1575's chatEdit reasons (already compliant — absorb,
  don't rewrite).

## Traps

- Do not regex-rewrite stored history — classification happens where messages are SHOWN or
  CREATED, never by migrating old rows.
- `strict: false` — no discriminated unions; use optional fields.
- Keep the classifier pure and dumb (string/class in, verdict out) so 1581 can call it from anywhere
  without imports going backwards.
