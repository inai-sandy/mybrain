# BEA-1608 — ship.sh "rollback" after a UI-gate failure is not a rollback

Linear: <https://linear.app/beakn/issue/BEA-1608>
Independent. Tooling only (`.claude/checks/*`), no app code.

## Why

Seen live 2026-09-03 during BEA-1603's ship. The UI gate failed; `ship.sh` (~L112-135, the gate block)
ran `.claude/checks/deploy.sh --rollback 2>/dev/null` and printed "Rolled back to the previous build,
so the live site is not left looking broken." But `deploy.sh` (120 lines, `set -euo pipefail`, `IMAGE=
mybrain-app:latest`, `PREV_IMAGE=mybrain-app:prev`) parses NO arguments — the only rollback code is the
inline health-check fallback (~L104-117) that fires only when the NEW container is unhealthy. So the flag
was ignored, `deploy.sh` did a normal deploy — built the image from the branch's working tree AGAIN — and
the same unreviewed build stayed live (verified: the live JS bundle carried the branch's new string after
the "rollback"). Second gap: `uicheck.sh` ~L152 runs `refresh-ui-session.sh >/dev/null 2>&1`, so a failed
login refresh is silent and the gate photographs a login page (attempt 1 of BEA-1603 walled that way).
Third: `preflight.sh` (144 lines) never checks the rollback path at all (no "rollback" in it).

## Guardrail — the owner's goal

"Finish without bugs and without disturbing the present running agent creation and running code."
This issue touches ONLY `.claude/checks/deploy.sh`, `ship.sh`, `uicheck.sh`, `preflight.sh` (+ a small
spec/shell test if the project has a place for one). No `api/`, no `web/`. **Deploying kills in-flight
agent runs** (CLAUDE.md) — before ANY deploy, rollback or rehearsal, check read-only that no `AgentRun`
is `running` and no `FlowRun` is `running` (query the live SQLite through the container as the other
briefs do); if one is, wait for it. Never run an agent. Never git by hand — ship.sh only (yes, you are
editing ship.sh; prove the edited scripts in rehearsal BEFORE shipping with them, see below).

## What to build

1. **`deploy.sh --rollback` is a real path.** Parse `$1`: with `--rollback`, do NOT build; require
   `mybrain-app:prev` to exist (else exit 2 with "no previous image to roll back to — the site is live
   with the current build"); re-tag `prev` → `latest`, `run_container`, `ensure_caddy`, `wait_healthy`;
   exit non-zero if it does not become healthy; on success print what is live (image id). Add
   `--rollback --dry-run` (or `--check-rollback`): prints whether `prev` exists and exits 0/2 without
   touching anything — for preflight. The normal (no-arg) path is byte-for-byte the same behaviour as
   today, including keeping the currently-live image as `prev` before overwriting the tag (~L87).
2. **`ship.sh` tells the truth.** In the gate-failure block: call `deploy.sh --rollback` WITHOUT
   `2>/dev/null` (its output is the evidence); on exit 0 print "Rolled back — live is the previous build
   (<image id>)"; on non-zero print "Could NOT roll back — the site is live with THIS build (<image id>)"
   and still exit 1. Never print "Rolled back" on a sentence it has not verified.
3. **`uicheck.sh` fails loudly on a failed login refresh.** Replace the silenced call at ~L152: run the
   refresh, capture its output; if it exits non-zero, print `== UI CHECK FAILED == (could not log in:
   <refresh's own message>)` and exit 1 BEFORE any screenshot. Keep everything else as it is.
4. **`preflight.sh` proves the rollback path** with `deploy.sh --rollback --dry-run`: reports "rollback
   ready (prev image present)" or, as WORTH KNOWING, "no previous image yet — a failed gate could not roll
   back". Do not turn a missing `prev` into a blocker (first deploy has none).
5. **Rehearsal proves it before it is used for real.** With no agent run in flight: (a) `ISSUE=TEST`
   rehearsal (`ship.sh TEST …` — `REHEARSAL=1` at ~L28-29 skips commit/merge/push) with the EDITED
   scripts on a throwaway route — it must exercise deploy + health + gate; (b) then a real `deploy.sh
   --rollback` once (prev = the build before yours, latest = yours are the same code today, so the site
   flips between two equivalent images; verify the live image id changes to the prev id, then run the
   normal `deploy.sh` to put latest back) — write both outcomes in your report with the image ids.

## Acceptance (WHEN / MUST)

- WHEN the UI gate fails, the live site MUST be the previous image (image id printed and verifiably
  different from the failed build's), and ship.sh MUST say so; WHEN `prev` is missing, ship.sh MUST say
  the site is live with the new build and that it could not roll back.
- WHEN the gate's login refresh fails, uicheck.sh MUST fail with the refresh's reason and MUST NOT take
  a screenshot.
- WHEN `deploy.sh` is run with no arguments, its behaviour MUST be unchanged (same tag dance, same health
  wait, same rollback-on-unhealthy).
- `preflight.sh` MUST report the rollback readiness; a missing `prev` MUST NOT block.
- Locking tests: a shell test (bats-style or a plain bash script under `.claude/checks/tests/` run by the
  project's test command, or a jest spec in `api/src/` that runs the scripts with a stubbed `sudo docker`
  on PATH — pick what the repo already has a pattern for) covering: `--rollback` with no prev → exit 2 +
  message; `--rollback` with prev → tag + run + health; `--dry-run` never touches docker run; uicheck
  fails loudly when the refresh exits 1. Existing suites stay green.
- MUST NOT touch `api/` or `web/`; MUST NOT deploy while an agent or flow run is `running`.

## Traps

- `ship.sh` is the thing you are editing AND the thing that ships you: test in rehearsal first; if the
  edited ship.sh breaks mid-ship, the fix is to re-run the same command after fixing — never git by hand.
- `deploy.sh` runs `set -euo pipefail`: an unset `$1` must be handled (`${1:-}`).
- `sudo docker` is password-free for sandy; never `2>/dev/null` a counting check.
- The gate cookie can wall even after a refresh — on a wall, refresh once and retry once, then park.
- UI_ROUTES is SPACE-separated. For your own ship use `UI_ROUTES="/agent"`.
