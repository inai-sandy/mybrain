# BEA-1596 — Needs You: ONE inbox for Tasks + Dashboard; the old `Reminder.needsOwner` flag is retired

Linear: <https://linear.app/beakn/issue/BEA-1596>
Independent. BEA-1597 (extras) ships after this.

## Why

Owner, 2026-09-02: "when my team requires my attention it is not showing up in Needs You — but it
IS showing on my dashboard." Confirmed on the live DB the same morning: Dashboard listed 4 people
(Rakesh, Jayanth ×2, Deepthi); Tasks → Needs you had 0 items.

The two screens read two different tables written by two independent judgements:

- **Tasks → Needs you** = `web/src/pages/ReviewInbox.tsx` → `GET /api/reminders/review` →
  `TeamUpdatesService.inbox()` (`api/src/contacts/team-updates.service.ts` ~L117):
  `teamUpdate` where `needsYou && closedAt == null && (taskId null || task.status == 'open')`.
  This is THE inbox (BEA-1159: "it closes ONLY when he closes it").
- **Dashboard** = `web/src/pages/Dashboard.tsx` → `GET /api/home` → `api/src/home/home.service.ts`
  ~L117: `reminder` where `needsOwner && status == 'active'` → row "X needs a reply", href
  `/contacts`. That is the OLD flag BEA-1159 meant to retire (see the header comment in
  team-updates.service.ts).
- Writers of the old flag that never create an inbox row:
  (a) the chase agent's `parsed.needsSandeep` branch, `api/src/contacts/reminder-agent.service.ts`
  ~L551-554 (`reminder.updateMany({ data: { needsOwner: true } })`);
  (b) the unanswered-reply watchdog escalation, same file ~L202 (contact-wide `needsOwner: true`,
  no message row at all — this is what flagged Rakesh + Jayanth at 00:00 IST 2 Sept).
  (c) Closing an inbox item (`team-updates.service.ts` ~L395 `close()`) never clears `needsOwner`,
  so Deepthi's "Need 298usd…" (closed 31 Aug) and Jayanth's 18 Aug update still show on Dashboard.

## What to build — the inbox is the single source of truth

1. **Every path that flags the owner records a `TeamUpdate` with `needsYou: true`** through
   `TeamUpdatesService.record()` (its 60 s dedupe stays):
   - `needsSandeep` branch: record the contact's last inbound message, `channel: 'whatsapp'`,
     `taskId` = the task of the reminder the model named (`needsItem` → `stuckOn`), falling back to
     null when it could not tell. Force `needsYou: true` on that row even if `readUpdate()` would
     have said "chat" — the agent already judged it (add a `forceNeedsYou?: boolean` input, or
     equivalent, decided in ONE place inside `record()`).
   - watchdog escalation: record ONE synthetic update per escalation, `channel: 'system'` (extend
     the channel union), text `No reply for 24 h — "<last inbound message, first 120 chars>"`,
     `needsYou: true`, `skipAi: true`. Never re-record on later ticks (the `escalated` set already
     guards this; make the record call sit inside that guard). `at` = now.
   - Both keep their existing `notifyOwner` push.
2. **`/api/home` `needsYou` reads the inbox.** Replace the `reminder.needsOwner` source in
   `home.service.ts` with `TeamUpdatesService.inbox()` items (inject the service; it is in
   ContactsModule — export it if needed). Row shape: `kind: 'team'`, icon `💬` (system rows `⏳`),
   title `<contact name>: <text first 60 chars>`, sub = the existing `label` from the inbox item,
   href `/tasks?tab=review`, action `Reply`. Keep NEED_RANK ordering (put `team` where `reminder`
   was, rank 1) and the per-source cap (take 5). Remove the `reminder` kind entirely.
   `Tasks.tsx` reads `tab` from the URL via `useUrlState('tab', …)`, so `/tasks?tab=review` lands
   on the Needs you tab — verify, don't assume.
3. **Retire `Reminder.needsOwner` as a READ source everywhere.** `home.service.ts`,
   `api/src/contacts/reminders.service.ts` (~L653, ~L686, ~L1077 `needsYou: !!r.needsOwner`), and
   any web reader (`grep -rn needsOwner web/src`). Where a per-contact / per-reminder "needs you"
   badge is needed, derive it from the inbox query (`contacts.service.ts` ~L73 already does exactly
   this — reuse that shape, never a second filter). Stop WRITING the flag everywhere
   (`reminders.service.ts` ~L294/319 clears, `delegation.ts` ~L112 clear, the two writers above).
   Keep the Prisma column (no destructive migration).
4. **Clear the stale flags once.** A one-off, idempotent startup step (or a Prisma migration with
   SQL) sets `needsOwner = false` on every reminder, so the Dashboard is honest the moment this
   ships and no leftover reader can resurrect the 4 ghosts.
5. **Close clears everything.** Closing in the inbox (`close()` → `closedAt`) is the only clear.
   `delegation.ts` ~L104 keeps stamping `closedAt` when a task finishes; drop its `needsOwner`
   clear.

## Acceptance (WHEN / MUST)

- WHEN a teammate's message is judged "needs Sandeep" by the chase agent, it MUST appear in
  Tasks → Needs you AND in Dashboard → Needs you, with the same text.
- WHEN the watchdog escalates an unanswered reply (24 h), an item "No reply for 24 h — …" MUST
  appear on both surfaces exactly once and MUST NOT duplicate on later watchdog ticks.
- WHEN the owner closes an item in the inbox, it MUST leave both surfaces on the next load.
- WHEN a routine report ("Today work SPD-300 qty") arrives, it MUST NOT open an item (existing
  spec stays green).
- WHEN this ships, the Dashboard MUST show zero "needs a reply" rows from the old flag: the 4
  live stale flags are cleared by the one-off step, and `GET /api/home` returns no `kind:'reminder'`.
- MUST NOT read `Reminder.needsOwner` anywhere after this (a spec greps the source for
  `needsOwner` outside schema + the one-off clear + `reminder-agent`'s deleted lines — like
  `needs-you-per-task.spec.ts` does with `readFileSync`).
- Locking tests: `team-updates.service.spec.ts` (+ cases: forced needs-you record; system watchdog
  row; dedupe on second escalation), `home.service.spec.ts` (needsYou `team` rows come from the
  inbox; a closed update is absent; `reminder` kind gone), `needs-you-per-task.spec.ts` rewritten
  to assert the flag lands on the inbox row for the named item (its BEA-1297 intent survives).
  All suites green: `.claude/checks/test-command`.
- UI routes for the gate: `/dashboard,/tasks?tab=review` (check the real dashboard path in
  `web/src` routes — use what exists).

## Traps

  `readFileSync` and asserts `needsOwner` update shapes — it WILL fail when the writer moves. Rewrite
  it to assert the new shape (inbox row for the named item, contact-wide fallback), don't delete it.
- `home.service.spec.ts` ~L62-69 asserts `kinds` contains `'reminder'` and a Srikar title — update
  to the `team` kind from an inbox fixture.
- Spec harnesses build services positionally (see the constructor comment in
  team-updates.service.ts) — add new deps LAST and optional.
- `record()` staples `taskId` from the FIRST reminder with a task (`items.find(it => it.taskId)`)
  — for the needsSandeep path pass the named item's task instead; do not "fix" the generic path.
- Watchdog runs every tick: the record must be inside the `!this.escalated.has(contactId)` guard,
  and `escalated` is in-memory — after a restart a second synthetic row within 60 s is deduped by
  `record()`, but one after a day is legitimately a new escalation. Accept that.
- Owner's rule: never sudo+`2>/dev/null` in a counting check; never do git by hand — ship.sh only.
- Two Claude sessions may share this checkout — verify on disk before assuming a file's state.
