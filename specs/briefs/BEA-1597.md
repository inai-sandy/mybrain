# BEA-1597 — Needs You extras: reason line, questions without "?", reply from the Dashboard

Linear: <https://linear.app/beakn/issue/BEA-1597>
Ships AFTER BEA-1596 (the inbox is the one source; Dashboard rows are `kind:'team'` from
`TeamUpdatesService.inbox()`).

## Why

Owner-approved 2026-09-02 as the follow-on to the Needs You fix: the list must say WHY each item
needs him, must catch questions his team writes without a question mark, and he wants to answer
from the Dashboard without leaving it.

## What to build

### 1. Reason line on every inbox item
Each item shows a short plain-English "why" on BOTH surfaces (Tasks → Needs you, Dashboard):
"asked for money", "asked you a question", "claims done — needs your check", "no reply for 24 h",
"stuck / blocked", "needs your decision". Source = the `reads` array stored on `TeamUpdate`
(kinds from `api/src/contacts/update-read.ts` + the AI second opinion) plus the `system` channel
row from BEA-1596. The kind → wording map lives in ONE place: the existing `readLabel()` (used at
`team-updates.service.ts` ~L476 — find where it is defined and extend it there). Never a second
table in the web app. `ReviewInbox.tsx` renders it under the message; the Dashboard row's `sub`
already carries the inbox `label` after BEA-1596 — make sure it is this same string.

### 2. Question detection without a trailing "?"
Today `update-read.ts` (~L49, the `TROUBLE` list) catches a question only via `/\?\s*$/` — a
literal `?` at the very END of the whole message, no multiline. Widen so these read as `needs_you`:
- a `?` anywhere in the text, per line (`/\?/m` on a line that has ≥ 2 words);
- ask-phrases without `?`: "pls confirm", "please confirm", "let me know", "can we", "shall we",
  "should i", "what is", "which one", "how much", "kindly advise", "waiting for your",
  "need your", "pls check", "please check";
- a request that names the owner ("sandeep", "sir pls…").
Keep the routine-report guard — the spec "a routine report never reaches the inbox" and a status
line whose product code contains "?" MUST NOT flip. Word lists stay in `update-read.ts` (plain
English, short), no model call added.

### 3. Reply from the Dashboard
A Dashboard needs-you row of `kind:'team'` opens the SAME reply sheet the inbox uses, in place, and
offers the same Close. Reuse, don't rebuild: `ReviewInbox.tsx` posts to
`/api/reminders/review/:id/reply`, `/decide`, `/close`. Lift the reply/close UI into a shared
component (`web/src/components/…`, follow the existing Sheet + scroll-lock rules — never add a
per-modal body lock) and use it in both pages. After reply/close the Dashboard strip refetches
`/api/home`. The row's `href` remains `/tasks?tab=review` for a plain tap on the text; the
"Reply" action button opens the sheet.

## Acceptance (WHEN / MUST)

- WHEN an item is in Needs you, it MUST show a one-line reason on Tasks AND Dashboard, and the
  wording MUST come from the single `readLabel()` map (a spec asserts both surfaces use it).
- WHEN a teammate writes "sir what is the budget for the Elleys order" (no `?`), it MUST open a
  Needs-you item; WHEN they write "pls confirm the qty" it MUST; WHEN they write
  "Today work SPD-300 qty" or "Magnetic 8+1-100 Qty" it MUST NOT.
- WHEN the owner taps Reply on a team row on the Dashboard, the reply sheet MUST open in place, a
  sent reply MUST go out through the existing `/reply` path, and Close MUST remove the row from
  both surfaces on refetch.
- Locking tests: `update-read.spec.ts` (each new phrase + two negatives), `team-updates.service.spec.ts`
  (label per kind incl. system), a web test for the shared reply component (render + calls the
  right endpoint). All suites green.
- UI routes for the gate: `/dashboard,/tasks?tab=review` (as in BEA-1596). Check table AND card
  views at 1180 + 390, and dark mode.

## Traps

- Widening detection changes what the AI second opinion sees — it runs only when regexes are
  unsure; make sure a positive regex hit still short-circuits it (no extra model calls).
- Don't over-catch: "?" inside product codes / URLs; require ≥ 2 words on the line.
- Modals: shared ref-counted body scroll lock via Sheet (`scrollLock.ts`) — never per-modal.
- Never do git by hand — ship.sh only. Two sessions may share this checkout — verify on disk.
