# BEA-1581 — plumbing failures phone home

Linear: <https://linear.app/beakn/issue/BEA-1581>
Depends on BEA-1580's classifier (`plumbingClassOf` and the plumbing classes as data) — it ships first.

## Why

Every bug this week was found because the owner IS the user. A paying myemo customer will not
report *"no readable meta.json"* — he will churn. When OUR plumbing fails on a customer's instance,
WE must hear about it before he writes in.

## Where

- NEW small seam, e.g. `api/src/push/ops-alert.ts` — ONE function `opsAlert({klass, agentId, runId,
  message})`; transport registered at boot via a setter (the `setOwnerAlertTelegram` pattern —
  Telegram → Daily → Mentor → Push, NEVER back; PushModule/others may not import TelegramModule).
  Today's transport: the app's existing `TelegramService` (it already delivers his watchdog and
  pause alerts, so it is configured and proven). Include an instance id (env `INSTANCE_ID`, default
  `mybrain`) in the message so the myemo control plane can swap transports later without touching
  call sites.
- Call sites: exactly where BEA-1580's classifier says plumbing-class — the detection points in
  `worker-dispatch` (runner unreachable / kit refused fallbacks), `worker-build` (meta unreadable,
  runner refusals), `worker-repair` (repair could not even start), `worker.controller`
  (NOT_REPEATABLE), the boot reconciler and sweeper (orphans swept). Use the classifier to decide —
  never a second hand-kept list (one rule, one home).

## Acceptance (WHEN / MUST)

- WHEN a plumbing-class failure happens, ONE ops alert goes out with: instance id, failure class,
  agent/run id, and the honest internal message.
- Dedupe per (class, agentId) per local day — one alert, not one per retry tick. In-memory is
  acceptable (a restart re-alerting once is fine); say so in a comment.
- MUST NOT alert on customer-actionable failures (bad goal, disconnected tool, vendor down —
  those are his six moves or a wait).
- The alert leg MUST NOT throw into the path it observes (`.catch(() => undefined)` like every
  alert leg in the codebase).
- A locking test: plumbing failure → exactly one transport call that day for that (class, agent);
  second occurrence same day → none; customer-actionable failure → none; transport throwing →
  the observed path still completes.

## Traps

- Module import direction is the hard rule here — a setter at boot, never an import of
  TelegramModule from the worker/push side.
- Do not alert from inside a test-driven path in specs — stub the transport as every alert test
  does; never send a real Telegram from the suite.
- The sweeper fires on a schedule: without the dedupe key including the DAY, a stuck plumbing state
  would alert every tick.
