# BEA-1407 — Brief First 3/6: Codex builds from the brief and the whole transcript

Part three of **Brief First**. Plan: <https://claude.ai/code/artifact/5c17fc65-a717-43b3-9bc6-4221968b0d94>
Linear: <https://linear.app/beakn/issue/BEA-1407>
Needs 1/6 (BEA-1405).

## Why

The Agent Workers machine (BEA-1386→1395, `specs/AGENT-WORKERS.md`) already compiles an agent into a
real program with Codex, tests it against saved answers, repairs itself and asks the owner on
WhatsApp. **It is fed by the eight-box form.** So Codex faithfully compiles a plan that already lost
the owner's actual request. This piece points it at the brief instead.

## Build

The build turn's payload becomes, in this order:

1. **The brief** — approved, one page, plus a line stating plainly that **where the brief and the
   transcript disagree, the brief wins**.
2. **The whole transcript** — every turn, in order, nothing summarised, struck lines **marked
   struck**. (Owner's decision, 2026-08-22: he wants Codex to see the full conversation, not a
   squeezed summary. The brief on top is what stops Codex building the ideas he killed.)
3. **Real saved answers** (`ToolSample`) for every action the brief names.
4. **The tool rulebooks** — `ToolKnowledgeService` cards: parameters, types, **defaults**, enums,
   paging, and known traps.

`default` must be a first-class field on the card, separate from `example`. An argument the plan
leaves out takes the vendor's default, and `gmail.fetch_emails.max_results` defaults to **1** — the
silent data-loss default that made the owner's nightly summary read one email a night for weeks.

**A program, not a form.** The brief may ask for things the old plan could not express, and the
generated worker must be able to do them:

- keep fetching pages until there are none left (no 11-page cap);
- group and sort rows any way the brief describes;
- compose the **exact outgoing message text** from the brief;
- run steps in any order, including "look at this, then decide what to fetch next".

**Codex still never calls a vendor.** It calls back into the app (`/api/worker/tool`) and the app
makes the real call with the owner's login. No key ever reaches the worker.

**`contract.json` is written by the APP, from the brief's `success` lines** — never by Codex. A
model-invented contract can be as wrong as the bug it exists to catch.

Editing an approved brief marks the worker **stale** and offers Rebuild; a stale worker keeps running
until rebuilt, never silently ignored.

An agent created from a brief is created with `useWorker: true`. The nine existing agents stay
`useWorker: false` and keep running the old road.

## Acceptance (WHEN / MUST)

- WHEN a worker is built from a brief, the payload Codex received MUST contain every transcript turn
  and MUST mark every struck line.
- WHEN the brief says "all emails since yesterday", the built worker MUST page until the source is
  exhausted — proved against a saved multi-page answer, with zero live calls.
- WHEN the brief names an exact message, the built worker MUST produce that message text (asserted
  against a saved answer).
- WHEN `contract.json` is written, its rules MUST come from the brief's `success` lines and MUST NOT
  be authored by Codex.
- WHEN the brief and transcript conflict, the built worker MUST follow the brief.
- WHEN an approved brief is edited, the worker MUST be marked stale.
- WHEN a build cannot pass its own tests, the agent MUST stay on its previous road and say so plainly.

## Notes

- One fresh `codex exec -s workspace-write` per build, `-C` the version folder, promote on green
  tests only — the existing rules in `specs/AGENT-WORKERS.md` stand.
- Plain English in everything the owner reads.
